<explanation>

- Em baixo nível, a memória da aplicação é um array de bytes.
- O ambiente de execução geralmente a divide, entre outras regiões, em:
    - **pilha**: memória pequena e de baixo custo,<sup>1</sup> onde fica a maioria das variáveis;
    - **heap**: memória grande e flexível, acessada por representantes na pilha, como `Box<T>`;
    - **estática**: usada frequentemente para armazenar a parte `str` de `&str`;
    - **código**: onde ficam as instruções das funções.
- A parte mais delicada está em **como a pilha evolui**, que será **nosso foco**.

<footnotes>

<sup>1</sup> Para valores de tamanho fixo, a pilha é simples de gerenciar: reserve alguns bytes enquanto forem necessários e libere-os ao sair. Porém, fornecer ponteiros para essas posições temporárias é justamente o motivo da existência dos lifetimes, tema do restante deste capítulo.

</footnotes>

</explanation>

<explanation>

```
let t = S(1);
```

- Reserva uma posição de memória chamada `t`, do tipo `S`, contendo o valor `S(1)`.
- Se declarada com `let`, essa posição fica na pilha. <sup>1</sup>
- Observe a **ambiguidade** de **variável**: a palavra pode indicar:
    1. o **nome** da posição no código-fonte, como em “renomear a variável”;
    1. a **posição** no programa compilado, `0x7`, como em “obter o endereço da variável”;
    1. o **valor** contido nela, `S(1)`, como em “incrementar a variável”.
- Para o compilador, `t` pode significar a **posição de** `t`, aqui `0x7`, ou o **valor em** `t`, aqui `S(1)`.

<footnotes>

<sup>1</sup> Como acima,{{ above(target="/language-constructs/data-structures/#data-structures" ) }} isso vale para código totalmente síncrono. Um quadro de pilha `async` pode ser colocado no heap pelo ambiente de execução.

</footnotes>


</explanation>

```
let a = t;
```

- Isso **move** o valor de `t` para a posição de `a`, ou o copia se `S` for `Copy`.
- Depois do movimento, a posição `t` fica **inválida** e não pode mais ser lida.
    - Tecnicamente, seus bits não estão vazios, mas indefinidos.
    - Se ainda fosse possível acessar `t` por `unsafe`, eles poderiam parecer um `S` válido, mas
    qualquer tentativa de usá-los como um `S` válido é comportamento indefinido. {{ below(target="/coding-guides/unsafe-unsound-undefined/#unsafe-unsound-undefined") }}
- Não trataremos explicitamente de tipos `Copy`. Eles mudam um pouco as regras:
    - não passam por descarte;
    - nunca deixam uma posição de variável vazia.

</explanation>

<explanation>

```
{
    let mut c = S(2);
    c = S(3);  // <- Drop called on `c` before assignment.
    let t = S(1);
    let a = t;
}   // <- Scope of `a`, `t`, `c` ends here, drop called on `a`, `c`.
```

- Quando o nome de uma variável que ainda contém um valor sai do **escopo de descarte**, seu valor é **descartado**.
    - Como regra prática, a execução chega ao ponto em que o nome sai do bloco `{}` em que foi definido.
    - Os detalhes são mais complexos, especialmente para valores temporários.
- O descarte também ocorre quando um novo valor é atribuído a uma posição de variável já ocupada.
- Nesses casos, **`Drop::drop()`** é chamado para a posição desse valor.
    - No exemplo, `drop()` é chamado para `a`, duas vezes para `c` e nenhuma para `t`.
- A maioria dos valores que não são `Copy` é descartada; exceções incluem `mem::forget()`, ciclos de `Rc` e `abort()`.

</explanation>


- Um **tipo de referência**, como `&S` ou `&mut S`, pode armazenar a **posição de** algum `s`.
- Aqui, o tipo `&S`, vinculado ao nome `r`, contém a posição da variável `a` (`0x3`), que deve ter tipo `S`, obtida por `&a`.
- Se a variável `c` é uma posição específica, a referência **`r` permite selecionar entre posições**.
- Como o de outros valores, o tipo da referência geralmente pode ser inferido; por isso, podemos omiti-lo a partir daqui.
    ```
    let r: &S = &a;
    let r = &a;
    ```
<!-- - References on their own are **never** concerned with the _value within_ the location they point to. -->

- Toda entidade de um programa tem alguma extensão temporal ou espacial em que é relevante, isto é, está viva.
- Informalmente, esse tempo de vida pode ser:<sup>1</sup>

```
// f1sm<'b, 'a>(rb: &'b     &'a     S) -> &'b mut S { *rb } // M
// f2sm<'b, 'a>(rb: &'b     &'a mut S) -> &'b mut S { *rb } // M

// Return long ('a) reference.
fn f1lr<'b, 'a>(rb: &'b     &'a     S) -> &'a     S { *rb }
// f2lr<'b, 'a>(rb: &'b     &'a mut S) -> &'a     S { *rb } // L
fn f3lr<'b, 'a>(rb: &'b mut &'a     S) -> &'a     S { *rb }
// f4lr<'b, 'a>(rb: &'b mut &'a mut S) -> &'a     S { *rb } // L

// Return long ('a) mutable reference.
// f1lm<'b, 'a>(rb: &'b     &'a     S) -> &'a mut S { *rb } // M
// f2lm<'b, 'a>(rb: &'b     &'a mut S) -> &'a mut S { *rb } // M
// f3lm<'b, 'a>(rb: &'b mut &'a     S) -> &'a mut S { *rb } // M
// f4lm<'b, 'a>(rb: &'b mut &'a mut S) -> &'a mut S { *rb } // L

// Now assume we have a `ra` somewhere
let mut ra: &'a mut S = …;

let rval = f1sr(&&*ra);       // OK
let rval = f2sr(&&mut *ra);
let rval = f3sr(&mut &*ra);
let rval = f4sr(&mut ra);

//  rval = f1sm(&&*ra);       // Would be bad, since rval would be mutable
//  rval = f2sm(&&mut *ra);   // reference obtained from broken mutability
//  rval = f3sm(&mut &*ra);   // chain.
let rval = f4sm(&mut ra);

let rval = f1lr(&&*ra);

//  rval = f3lm(&mut &*ra);   //                    "
```

- Os casos `f_lm` sempre falham por uma combinação dos motivos acima.

<explanation>

```
{
    let f = |x, y| (S(x), S(y)); // Function returning two 'Droppables'.

    let (    x1, y) = f(1, 4);  // S(1) - Scope   S(4) - Scope
    let (    x2, _) = f(2, 5);  // S(2) - Scope   S(5) - Immediately
    let (ref x3, _) = f(3, 6);  // S(3) - Scope   S(6) - Scope

    println!("…");
}
```

<footnotes>

Aqui, `Scope` indica que o valor contido vive até o fim do escopo, além de `println!()`.

</footnotes>

- Valores movíveis produzidos por funções ou expressões precisam ser tratados por quem os recebe.
- Valores armazenados em vínculos comuns permanecem até o fim do escopo e então são descartados.
- Valores armazenados em vínculos `_` geralmente são descartados imediatamente.
- Porém, referências como `ref x3` podem prolongar a existência de valores como a tupla `(S(3), S(6))`. Assim, `S(6)`, que faz parte da tupla, só pode ser descartado quando a referência ao campo irmão `S(3)` deixar de existir.
